# 관리자 매뉴얼 — 노션 템플릿 기획·설명서 생성기

이 문서는 프로그램을 **쓰는 쪽**(관리자)이 봅니다.
템플릿 구매자에게 그대로 주는 문서는 산출물의 `user_manual.md` 입니다.

---

## 1장. 노션 템플릿이 팔리는 구조

### 돈이 어디서 나오는가

노션 템플릿은 단가가 낮습니다. 1~3만 원대가 대부분입니다.
그래서 **한 개를 잘 만들어 오래 파는 것**과 **파생을 만드는 것** 두 가지로 벌게 됩니다.

| | 특징 |
|---|---|
| 한 개를 오래 | 재고가 없고 배송이 없습니다. 만들어 두면 계속 팔립니다 |
| 파생 만들기 | 구조는 그대로, 타깃과 낱말만 바꿉니다. 처음의 10~20% 시간 |
| 1:1 세팅 | 객단가를 5~10배로 올립니다. 적게 팔려도 매출이 큽니다 |

**가격 3안 중 가운데가 가장 많이 팔립니다.** 낮은 안은 문턱을 낮추고,
높은 안(맞춤 세팅)은 객단가를 올립니다. `sales_page.md` 가 이 구조로 냅니다.

### 무엇이 값어치를 만드는가

표를 여러 개 만든 것과 템플릿의 차이는 **연결**에 있습니다.
프로젝트를 열었을 때 딸린 작업과 아직 안 받은 돈이 같이 보이는 것,
그게 사람들이 돈을 내는 이유입니다.

그래서 프롬프트가 **관계 2개 이상, 롤업 1개 이상**을 요구합니다.
이 조건을 낮추지 마세요. 연결이 없으면 무료 템플릿과 다를 바 없습니다.

## 2장. 어떻게 도는가

```
주제 + 타깃
   │
   ├─ [1] 구조 설계   Claude → spec.yaml (pydantic 검사)
   ├─ [2] 판매 문구   Claude → sales_page.md (금지 표현 검사)
   ├─ [3] 구매자 문서 Claude → user_manual / preview_brief / variants
   └─ [기계] build_guide.md ← 설계에서 그대로 만듭니다
```

Claude 호출은 **3회**입니다. 한 번에 1~2분, 비용은 수백 원 수준입니다.

### build_guide 를 Claude 가 쓰지 않는 이유

설명서가 설계와 어긋나면, 그 설명서를 따라 만든 사람이 중간에서 막힙니다.
사람이 쓴 설명서는 설계가 바뀌면 **조용히 낡습니다.**

그래서 `build_guide.md` 는 `spec.yaml` 에서 기계적으로 만듭니다.
속성이 하나 늘면 가이드에도 하나 늘고, 소요 시간도 자동으로 늘어납니다.
어긋날 수가 없습니다.

소요 시간은 `writers.MINUTES` 에 적힌 단가로 계산합니다. 실제로 만들어 보고
너무 짧거나 길면 그 값을 고치세요.

## 3장. 노션 API 로 못 하는 것 — 가장 중요한 장

이걸 모르고 설계하면 **납품 직전에 막힙니다.**

| | 공개 API |
|---|---|
| 페이지, 데이터베이스, 속성 | ✅ |
| 관계·롤업 | ✅ (단계를 나눠야 합니다) |
| 예시 데이터 행 | ✅ |
| **뷰 (표·보드·달력)** | ❌ **전혀 못 만듭니다** |
| **상태(status) 속성** | ❌ select 로 대신 만들고 알려 줍니다 |
| **템플릿 버튼** | ❌ |
| 고유 ID·확인 속성 | ❌ |

**뷰를 못 만드는 것이 가장 큽니다.** 템플릿의 쓸모는 대부분 뷰에서 나옵니다.
"오늘 할 일" 뷰, "미입금" 뷰 같은 것이요. 그런데 그건 전부 손으로 만들어야 합니다.

그래서 `deploy` 를 돌려도 **일이 절반쯤 남습니다.** 그 남은 일을 `deploy_log.md` 의
'손으로 해야 하는 것' 목록으로 내놓습니다. 고객에게 "자동으로 다 만들어 드립니다"
라고 하지 마세요. 사실이 아닙니다.

### 확인되지 않은 부분

이 목록은 공개 문서를 근거로 적었고, **이 저장소를 만든 컨테이너에서는
api.notion.com 에 닿지 못해 실제 호출로 확인하지 못했습니다.**

노션 API 는 조용히 바뀌는 편입니다. 처음 쓰실 때 빈 페이지에 한 번 돌려 보시고,
다르면 `notion_kit/notion_types.py` 의 두 목록만 고치면 됩니다.
그 파일 하나가 `deploy` 와 `build_guide` 양쪽의 판단 근거입니다.

## 4장. 관계를 두 단계로 나누는 이유

관계 속성은 **이을 상대가 이미 있어야** 만들어집니다. 그런데 데이터베이스를
만들면서 동시에 관계를 넣으려면 아직 없는 id 가 필요합니다.

```
1단계  관계·롤업을 뺀 나머지 속성으로 데이터베이스를 전부 만든다
2단계  id 를 다 알게 됐으니 PATCH 로 관계를 붙인다
3단계  관계가 생겼으니 롤업을 붙인다   ← 롤업은 관계를 타고 간다
4단계  예시 데이터를 넣는다
```

손으로 만들 때도 순서가 같습니다. `build_guide.md` 3단계가 그래서
"데이터베이스를 전부 만든 뒤에 하세요" 로 시작합니다.

### 순서를 어떻게 확인했나

노션 API 에 닿지 못하는 곳에서도 순서는 확인해야 했습니다.
그래서 테스트가 **노션인 척하는 작은 서버**를 띄우고, `deploy` 가 보낸 요청을
받아 적습니다. 무엇을 어떤 차례로 보냈는지 보면 순서가 맞는지 알 수 있습니다.

확인하는 것: 토큰 검사가 맨 앞인가 · 페이지가 데이터베이스보다 먼저인가 ·
데이터베이스를 만들 때 관계가 섞여 들지 않았는가 · 관계 PATCH 가 모든 DB 생성
뒤인가 · 롤업이 관계 뒤인가 · 예시 행이 맨 마지막인가.

## 5장. 실패했을 때

중간에 끊기면 노션에 **절반쯤 만들어진 것**이 남습니다.
무엇이 남았는지 모르면 지우지도 이어 만들지도 못합니다.

그래서 한 단계가 끝날 때마다 기록하고, 실패해도 그때까지를 `deploy_log.md` 로 남깁니다.

```
| 종류 | 이름 | 결과 | 비고 | 노션 id |
| 페이지 | 프리랜서 작업실 | ✅ | ... | `1a2b3c4d` |
| 데이터베이스 | 클라이언트 | ❌ | [400 validation_error] ... |
```

**다시 돌리기 전에 만들어진 페이지를 지우세요.** 노션은 같은 이름으로 또 만드는 것을
막지 않습니다. 안 지우고 다시 돌리면 두 벌이 생기고, 어느 쪽이 맞는지 헷갈립니다.

### 흔한 오류와 뜻

| 오류 | 뜻 | 조치 |
|---|---|---|
| `unauthorized` | 토큰이 틀림 | `.env` 의 NOTION_TOKEN 확인 |
| `restricted_resource` | 통합에 권한 없음 | **부모 페이지에서 ··· → 연결 → 통합 선택** |
| `object_not_found` | 페이지를 못 찾음 | 페이지 id 확인 + 위와 같은 연결 확인 |
| `validation_error` | 요청 모양이 안 맞음 | `spec.yaml` 을 `check` 로 먼저 검사 |
| `rate_limited` | 너무 잦음 | 잠시 뒤 다시. 프로그램이 알아서 기다립니다 |

**`restricted_resource` 가 가장 많이 나옵니다.** 토큰만 만들고 페이지에 연결하는
단계를 빠뜨리기 때문입니다. 안내 문구에 이 단계를 따로 적어 둔 이유입니다.

## 6장. 좋은 설계가 나오게 하는 법

### 타깃을 좁히세요

`--audience` 가 결과를 가장 크게 좌우합니다.

| 타깃 | 결과 |
|---|---|
| "1인 사업자" | 뻔한 구조. 아무에게도 안 팔립니다 |
| "1인 디자이너" | 쓸 만합니다 |
| "브랜딩만 하는 1인 디자이너" | 속성 이름까지 그 사람 말로 나옵니다 |

팔리는 이유는 사는 사람이 **"내 얘기네"** 라고 느끼기 때문입니다.
넓힐수록 그 느낌이 옅어집니다.

### 데이터베이스는 3~5개

2개면 템플릿이라 부르기 민망하고, 6개가 넘으면 구매자가 복제하고 나서 안 씁니다.
프롬프트에 이 범위를 박아 두었습니다.

### 속성은 DB 당 5~9개

많으면 안 채우게 되고, 안 채운 칸은 빈 화면이 됩니다.
빈 화면을 본 구매자는 "이거 별로네" 라고 생각합니다.

### 나온 설계를 그대로 쓰지 마세요

**반드시 읽어 보고 고치세요.** 특히 이 세 가지를 봅니다.

1. 데이터베이스 이름이 그 업계에서 실제로 쓰는 말인가
2. 첫 화면에서 "오늘 할 일" 이 보이는가
3. 안 쓸 것 같은 속성이 있는가 (있으면 지우세요)

## 7장. 만들고 나서

### 반드시 직접 만들어 보세요

`deploy` 로 만들었든 손으로 만들었든, **로그아웃 상태의 다른 브라우저로
복제 링크를 열어 보세요.**

가장 흔한 사고가 **공유를 안 켜고 링크를 파는 것**입니다.
구매자가 열면 "권한이 없습니다" 가 뜹니다. 환불과 별점 1개가 같이 옵니다.

`build_guide.md` 7단계에 이 점검이 들어 있습니다.

### 미리보기는 반드시 실제 화면으로

`preview_brief.md` 는 **그리라는 것이 아니라 찍으라는 지시서**입니다.
실제와 다른 이미지는 환불 사유이고, 플랫폼에 따라 제재 대상입니다.

예시 데이터에 **실제 고객 이름이나 실제 금액이 들어가지 않았는지** 꼭 보세요.
캡처에 그대로 찍힙니다.

### 노션 로고를 쓰지 마세요

노션 상표입니다. 썸네일에 넣고 싶어지지만 문제가 됩니다.

## 8장. 파생 템플릿을 어디까지 늘릴 것인가

`variants.md` 가 5개를 제안하지만, **3~4개가 적당합니다.**

그 이상은 관리가 안 됩니다. 템플릿마다 문의가 들어오고, 노션이 바뀌면 전부
손봐야 합니다. 열 개를 파는 것보다 세 개를 제대로 파는 쪽이 낫습니다.

그리고 **내가 모르는 직군으로 넓히지 마세요.** 질문이 들어와도 답할 수 없습니다.

> 같은 구조를 여러 타깃에 파는 것은 정상적인 방식입니다. 다만 내용 없이 개수만
> 늘리는 것은 다릅니다. CLAUDE.md §3 이 금지한 양산과 같은 종류의 일이 됩니다.
> 플랫폼도 구매자도 금방 알아봅니다.

## 10장. 문제 해결

| 증상 | 원인 | 조치 |
|---|---|---|
| `규격에 맞지 않았습니다` | 3번 모두 설계가 어긋남 | 주제를 좁히거나 `prompts/spec.md` 에 예시를 늘리세요 |
| 롤업 오류가 계속 남 | 관계와 롤업을 헷갈림 | `rollup_relation` 은 **같은 DB 의 관계 이름**입니다 |
| 판매 문구에 금지 표현 | 2번 재시도도 실패 | `sales_page.md` 의 점검 표를 보고 직접 고치세요 |
| deploy 가 `restricted_resource` | 통합을 페이지에 연결 안 함 | 부모 페이지 ··· → 연결 |
| deploy 후 뷰가 없음 | **정상입니다** | API 로 못 만듭니다. `build_guide.md` 4단계 |
| '진행' 이 상태가 아니라 선택 | **정상입니다** | 노션에서 타입을 '상태' 로 바꾸세요 |
| 두 벌이 생김 | 지우지 않고 다시 돌림 | 만들어진 페이지를 지우고 다시 |
| 예시 행의 관계가 비어 있음 | **정상입니다** | 어느 행끼리 이을지는 설계에 없습니다. 손으로 고르세요 |

## 11장. 규정 관련

- **AI 생성물 표시** — 산출 문서 5종에 기본으로 들어갑니다(인공지능기본법 제31조).
  `spec.yaml` 에는 넣지 않습니다. 기계가 읽는 파일이기 때문입니다.
  구매자에게 주는 `user_manual.md` 에는 표시가 남아 있어야 합니다. 지우지 마세요.
- **성과를 단정하지 않습니다** — 판매 문구에서 금지 표현을 검사하고,
  걸리면 그 표현을 짚어 다시 시킵니다. 끝내 안 되면 `sales_page.md` 점검 표에 적습니다.
- **베끼지 않습니다** — 남의 템플릿을 입력으로 받지 않습니다.
  주제와 타깃에서 구조를 새로 짭니다.
- **노션 계정 정보를 대신 받지 마세요** — 통합 토큰은 본인이 발급해 본인 `.env` 에
  둡니다. 고객 대신 만들어 드릴 때도 화면 공유로 고객이 직접 넣게 하세요.
- **비밀키** — `.env` 는 커밋되지 않습니다. `spec.yaml` 에도 토큰이 들어가지 않습니다.
